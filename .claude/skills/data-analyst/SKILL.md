# data-analyst — 자유 질문 분석 규칙

## 시작 전
1. **`hub/CATALOG.md` 를 먼저 읽는다.** 테이블·컬럼·키·정의를 추측하지 않는다. `?` 이거나 없으면 사용자에게 묻는다.
2. 질문이 `hub/engine/analysis.py` 의 함수(성분·의심 파트·PM 주기·SPEC OVER)에 맞으면 **그 함수를 그대로 호출**한다(검증된 부품).
3. 없으면 `hub/examples/pm_before_after.py` 와 같은 모양으로 새 분석을 `hub/analyses/<이름>.py` 에 쓴다.
4. 모호하면 먼저 묻는다(지표 정의, 기간, 설비 범위). 합리적 기본값이 있으면 **가정을 명시하고 진행**한다.

## 분석 코드 규칙
- 맨 위 `Session("<질문 그대로>")`, 데이터는 `s.src.<메서드>` 로만 가져온다(`hub/engine/sources.py`). DB 에 직접 접속하지 않는다.
- 표를 붙일 때는 `checks.safe_merge` 를 쓴다. **PM·파트처럼 시간으로 붙이는 건 `pd.merge_asof` 또는 구간 조건** — eqp_id 만으로 조인하지 않는다.
- 결과 표는 `s.table(df, "이름", time_col=..., expected=(시작, 끝), key=[...])` 로 점검·저장한다.
- 가정·정의는 `s.note("...")` 로 남기고 마지막에 `s.finish()`.
- **화면에 행 단위 데이터를 print 하지 않는다.** 집계 결과 위주로 본다(`HUB_PREVIEW_ROWS` 가 미리보기 행 수를 제한한다).
- 숫자는 코드 출력에서만 인용한다. 머릿속 계산·추측 금지.
- 금지: DB 쓰기·DDL, 조건·기간 없는 전체 조회, 실데이터를 저장소에 커밋, 외부로 전송.

## 답변 형식
1. **결론 한 줄** (확신도: 높음/중간/낮음)
2. **근거 수치** — 코드 출력의 숫자 그대로
3. **가정과 정의** (`s.note` 내용)
4. **자동 점검 경고** (있으면 반드시 그대로 전달. 없어도 "통과=맞다는 뜻 아님")
5. **한계** — 표본 수가 적거나(예: 한쪽 구간 3건 미만) 설비 몇 대뿐이면 일반화하지 않는다
6. 기록 위치: `hub/runs/<시각>_<질문>/summary.md`
7. 다음 확인 제안 1~2개

## 해석 원칙
- 원인은 **추정**이라고 쓴다. 단정하지 않는다("A 파트 불량이다" ✗ → "A 원소가 동료 대비 높아 A 파트를 우선 확인 권장" ✓).
- 근거가 없으면 "근거 부족"이라고 답한다. 질문자가 기대하는 답에 맞추려고 결론을 만들지 않는다.
- 같은 질문을 정형 함수로도 풀 수 있으면 두 결과가 일치하는지 확인한다(불일치 = 코드 오류 신호).

## 새 분석 승격
같은 종류의 질문이 반복되면 `hub/analyses/` 의 스크립트를 `hub/engine/analysis.py` 함수로 올리자고 제안한다(사람이 검토 후 반영).
